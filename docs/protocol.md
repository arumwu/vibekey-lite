# AU05 / VibeKey HID protocol notes

This document records protocol facts needed to interoperate with the Ulanzi
AU05 (marketed as VibeKey) over USB on macOS.

The information was reverse-engineered for interoperability from a connected
AU05's HID descriptors and read-only static analysis of Ulanzi Studio 3.3.6.
VibeKey Lite is an independent implementation. It does not contain, copy, load,
link, or redistribute `kwdm.dylib`, `UlanziDeck`, or any other vendor binary.

## Confidence labels

- **Device-observed**: read from the connected AU05 through IORegistry/HID
  properties.
- **Static-confirmed**: the 3.3.6 vendor host constructs or parses this exact
  layout. This proves host-side intent, not firmware behavior.
- **Vendor-runtime-observed**: the connected AU05 and vendor 3.3.6 runtime
  logged a matching request/response path. This does not prove that a report
  generated by VibeKey Lite has completed the same round trip.
- **Device-tested**: VibeKey Lite completed the operation against the connected
  AU05 and the resulting standard-HID behavior was observed.
- **Needs hardware test**: not yet established by a controlled AU05 capture or
  write/readback test.

Unless noted otherwise, every offset below is zero-based and refers to the
64-byte **plaintext**, before TEA encryption and before adding HID report ID
`0x55`. Unspecified bytes are zero.

## USB HID identity and interfaces

The connected AU05 exposes two HID interfaces with the same VID/PID.

| Property | Custom control interface | Standard HID interface |
| --- | --- | --- |
| Vendor ID | `0xFFF1` | `0xFFF1` |
| Product ID | `0x00DD` | `0x00DD` |
| Product / manufacturer string | `AU05` / `AU05` | `AU05` / `AU05` |
| Primary usage page | `0xFFFC` | `0x000C` (Consumer) |
| Primary usage | `0x0001` | `0x0001` |
| Report IDs | `0x55` | `0x01`, `0x02`, `0x03` |
| Max input report size | 64 bytes | 9 bytes |
| Max output report size | 64 bytes | 2 bytes |
| Purpose | Encrypted configuration and raw notices | Consumer, mouse, and keyboard HID reports |
| Confidence | Device-observed | Device-observed |

Match the custom interface by VID, PID, primary usage page, and primary usage.
Matching only VID/PID can select the standard interface by mistake.

The custom interface's report descriptor is:

```text
06 fc ff 09 01 a1 01 09 02 85 55 15 00 26 ff 00
75 08 95 3f 81 02 09 03 15 00 26 ff 00 75 08 95
3f 91 02 c0
```

The important fields are `85 55` (report ID `0x55`) and `95 3f` (63 data
bytes) for both input and output. A complete HID report is therefore 64 bytes:
one report-ID byte plus 63 report-data bytes.

## Custom report framing

### Output

Build and encrypt a 64-byte logical message, then send this 64-byte report:

```text
report[0]     = 0x55
report[1..63] = encryptedPlaintext[0..62]
```

On macOS, the vendor host calls `IOHIDDeviceSetReport` with all of the
following at once:

```text
reportType = kIOHIDReportTypeOutput
reportID   = 0x55
buffer     = [0x55] + encryptedPlaintext.prefix(63)
length     = 64
```

In other words, the report ID is passed as the API argument **and** is byte 0
of the 64-byte buffer. Passing 64 encrypted bytes without the leading `0x55`
does not match the vendor transport or the AU05 descriptor.

This is static-confirmed by `-[HidDevice sendData:value:]` in the arm64 slice
of `kwdm.dylib` at file address `0x27688`: it writes the report ID to byte 0,
reduces the data capacity from 64 to 63, copies at most 63 encoded bytes to
byte 1, then calls `IOHIDDeviceSetReport` with length 64.

### Input

The vendor input callback accepts either form defensively:

1. If byte 0 equals the callback's nonzero report ID, skip byte 0.
2. Otherwise, treat byte 0 as the first encrypted data byte.
3. Decrypt only complete 8-byte blocks.

If an AU05 callback buffer includes report ID `0x55` and has length 64, this
leaves 63 encrypted data bytes, so
only bytes `0..55` form seven complete TEA blocks. The last seven encrypted
bytes cannot form a block and are ignored by the vendor decoder. Protocol
headers, fixed fields, and the one-entry shortcut candidate documented below
are all below plaintext offset 56.

The input callback is `_InputReportCallback` at `0x27404`; its report-ID
normalization is at `0x2743c..0x27448`.

## TEA codec

The custom `0xFFFC` interface uses ordinary 32-round TEA independently on each
8-byte block. Both 32-bit words and key words are little-endian. Arithmetic
wraps modulo `2^32`.

```text
delta = 0x9E3779B9

key bytes =
ca ba a5 ca 6d 8a 2a bc ba 9e 5a ca ca 8b b8 9b

key words (little-endian) =
0xCAA5BACA 0xBC2A8A6D 0xCA5A9EBA 0x9BB88BCA
```

Encryption starts with `sum = 0` and performs 32 rounds:

```text
sum += delta
v0  += ((v1 << 4) + k0) ^ (v1 + sum) ^ ((v1 >> 5) + k1)
v1  += ((v0 << 4) + k2) ^ (v0 + sum) ^ ((v0 >> 5) + k3)
```

Decryption starts with `sum = 0xC6EF3720` and reverses those operations for 32
rounds. There is no IV, chaining, padding marker, visible length field, or
checksum in these short control messages.

Known first-block vectors:

| 8-byte plaintext block | 8-byte ciphertext block |
| --- | --- |
| `01 06 50 01 00 00 00 00` | `57 df 12 e6 02 d7 9d fd` |
| `01 0b 88 01 00 00 00 00` | `4e 3e 82 16 20 cf f3 ac` |
| `01 0b 89 04 01 00 00 00` | `2f fe 1a ad 13 00 5a 55` |
| `00 00 00 00 00 00 00 00` | `38 90 c4 99 a3 60 aa ad` |

The codec and framing are covered by local unit vectors. The key bytes and
shortcut vectors were verified at runtime against vendor 3.3.6 on an AU05.

## Request header

Short host requests share this header:

| Offset | Size | Meaning |
| --- | --- | --- |
| 0 | 1 | Request class, currently `0x01` |
| 1 | 1 | Command group |
| 2 | 1 | Command ID |
| 3 | 1 | Operation: `0x01` GET, `0x04` SET |

## Physical controls and raw key notice

The vendor application registers this AU05 position map:

| Logical index | Control |
| --- | --- |
| `0` | Top button |
| `1` | Middle button |
| `2` | Bottom button |
| `3` | Encoder press |
| `4` | Encoder clockwise / right |
| `5` | Encoder counter-clockwise / left |

A decrypted raw key notice has this layout. The top three bits of byte 0 may be
set, so identify the group with `(plaintext[0] & 0x1F) == 0x0B` rather than an
exact-byte comparison:

```text
?b 10 <logicalCode> <status> <physicalIndex> ...
```

| Offset | Size | Meaning |
| --- | --- | --- |
| 0 | 1 | Notice group: low five bits are `0x0B` |
| 1 | 1 | Key-event notice `0x10` |
| 2 | 1 | Logical code; not the AU05 slot number |
| 3 | 1 | Status |
| 4 | 1 | Physical index |

Connected-device captures included encoder-press packets
`8B 10 6E 01 03` (down) and `8B 10 6E 00 03` (up). Other captured pairs were
logical code `0x6F` with physical index `0`, and `0x70` with physical index
`1`. The physical index at offset 4 is therefore the authoritative AU05
control position. The vendor host maps status `1` to key-down/pressed and
status `0` to key-up/released for indexes `0..3`; it treats indexes `4` and `5`
as rotation events without consulting status. The layout and observed packets
are device-observed; repeat behavior remains unverified.

The generic library also parses notice `0B 1E` as up to eight nonzero signed
8-bit wheel deltas at offsets `2..9`. The AU05 application mapping uses key
positions `4` and `5` instead, so AU05 emission of `0B 1E` is unverified.

## On-device button configuration

These commands address the same zero-based button/index space.

### Function index

```text
GET: 01 06 10 01 00 <buttonIndex> 00 ...
SET: 01 06 10 04 00 <buttonIndex> <funcIndex:LE32> 00 ...
```

| Offset | Size | Meaning |
| --- | --- | --- |
| 5 | 1 | Button/index |
| 6 | 4 | SET function index, little-endian |

The byte layout is static-confirmed. The function-index enumeration and which
values AU05 firmware accepts need hardware testing.

### Shortcut / macro assignment

```text
GET: 01 06 50 01 <index> 00 ...
SET: 01 06 50 04 <index> 01 <count> <entry0> <entry1> ...
```

Each entry is two bytes:

```text
pageAndSign = (page & 0x7f) | ((sign & 1) << 7)
value       = one-byte usage/value
```

| Offset | Size | Meaning |
| --- | --- | --- |
| 4 | 1 | Target index |
| 5 | 1 | Fixed `0x01` in the vendor SET builder |
| 6 | 1 | Entry count |
| `7 + 2*i` | 1 | Entry `i` page in bits 0..6, sign in bit 7 |
| `8 + 2*i` | 1 | Entry `i` value |

The builder layout is static-confirmed. Its in-memory 64-byte buffer can hold
at most 28 complete pairs; it does not perform an explicit bounds check.
Implementations should use a much lower bound, keep all meaningful plaintext
below offset 56, and reject oversized input.

The static-confirmed layout for one keyboard F-key is:

```text
01 06 50 04 <index> 01 01 02 <keyboardUsage> 00 ...
```

USB keyboard usages F13 through F18 are `0x68..0x6D`. The vendor setter maps
ordinary keyboard usages, including that range, to byte-7 page code `0x02`;
modifier usages `0xE0..0xE7` instead use `0x03`. This selection is
static-confirmed. An earlier VibeKey Lite test wrote F18 (`0x6D`) to encoder
slot 3; its persistence and F18 down/up output on the standard HID interface
are device-tested. Acceptance of every other F13-F17
usage has not been established. Do not describe vendor page code `0x02` as USB
Usage Page `0x02`.

The vendor 3.3.6 runtime was also observed issuing six
`setDeviceButtonShortcutFunction2` requests to the connected AU05 and receiving
responses for indexes `0..5`. VibeKey Lite subsequently wrote full six-slot
profiles through this command family; native Left Option, Return, Escape, Tab,
arrow keys, command chords, and F18 were observed on the AU05. This path is
device-tested for those mappings. Current releases do not reserve F18.

## Indicator LED commands

All known indicator-light settings use group `0x0B`, command `0x88`.

```text
GET all: 01 0b 88 01 00 ...
SET:     01 0b 88 04 <fieldMask> <ledIndex> <payload> ...
```

SET fields are selected by one bit in plaintext offset 4:

| Mask | Value offset | Meaning |
| --- | --- | --- |
| `0x01` | 6 | Current/global mode |
| `0x02` | 7 | All-on-mode brightness |
| `0x04` | `8 + 5*ledIndex` | Work-mode type |
| `0x08` | `9 + 5*ledIndex` | Work time |
| `0x10` | `10 + 5*ledIndex` | Breathing level |
| `0x20` | `11 + 5*ledIndex` | Breathing brightness |
| `0x40` | `12 + 5*ledIndex` | Always-on brightness |

For per-LED fields, offset 5 is also set to `ledIndex`. The host allocates four
five-byte records (`ledIndex` 0 through 3), beginning at offset 8.

The command and offset layout is static-confirmed. Valid mode/type values,
brightness ranges, timing units, which physical light each LED index selects,
GET-response layout, and visible AU05 behavior all need hardware tests. Start
with GET/readback and low-risk values rather than guessing ranges.

The generic library also has brightness commands:

```text
GET: 01 06 20 01 00 ...
SET: 01 06 20 04 <brightness> 00 ...
```

Their existence is static-confirmed; applicability to AU05 is not.

## Read-only power information

VibeKey Lite reads these values for display and does not send the matching SET
commands. The connected AU05 returned a battery level of 30%, 3688 mV, a
300-second standby delay, and a 3600-second sleep/power-off delay.

| Value | GET plaintext header | Successful response payload |
| --- | --- | --- |
| Battery | `01 01 02 01` | voltage `u16le` at 4, percent `u16le` at 6, charging byte at 10, flags at 11 |
| Standby state | `01 01 0D 01` | Boolean at 4 |
| Standby delay | `01 01 2C 01` | seconds as `u32le` at 4 |
| Sleep / power-off delay | `01 01 42 01` | seconds as `u32le` at 4 |

Responses use group byte `0x81`, command group `0x01`, the corresponding
command ID, and status byte `0x11`. The low bit of the status byte denotes
success. These layouts are static-confirmed and the values above are
device-observed through read-only GET requests.

## Device hooks mode (`0x89`)

```text
GET: 01 0b 89 01 00 ...
SET: 01 0b 89 04 <mode> 00 ...
```

The vendor host passes its Boolean `m_aiHooksEnabled` directly as `mode`, so
the application-level meaning is:

| Mode | Vendor host state |
| --- | --- |
| `0` | AI hooks disabled/not available |
| `1` | AI hooks enabled/available |

This does **not** prove that `mode` is a firmware gate for raw `0B 10` key
notices. Static evidence points the other way at the host-transport layer:

- `-[HidDevice init:]` at `0x27060` unconditionally registers
  `IOHIDDeviceRegisterInputReportCallback` at `0x273bc`.
- `-[MessageHandler handleNoticeMessage:length:]` at `0x18d54` parses key
  notice `0x10` without checking hooks mode.
- The main application first sends the current Boolean only after it receives
  the device serial number (`UlanziDeck` call site `0x1006ba3ec`), after HID
  setup has already occurred.
- It sends the Boolean again when the CLI AI-hooks status changes (call site
  `0x1006cd3a0`).

A whole-executable direct-call search of the 3.3.6 `UlanziDeck` executable
found those two normal call sites only. Its destructor at `0x100675d78` has no
direct call that sends mode 0 or restores a prior value. Firmware
reset-on-disconnect or persistence cannot be inferred from this absence.

A later controlled AU05 test found that the host-online path exposed custom raw
notices while suppressing configured native controls. Hooks command `0x89` did
not independently expose raw reports and is not needed by VibeKey Lite. Future
hooks research must still GET and save the original mode before comparing modes
0 and 1, then restore that exact value; never assume restoring means writing 0.

## Relationship to standard HID / offline macros

The custom and standard HID interfaces enumerate simultaneously. Controlled
AU05 tests established the behavior used by VibeKey Lite:

- full profiles written through the custom interface remain native when the
  app is stopped;
- configured keyboard shortcuts generate standard keyboard report ID `0x03`;
- F18 at encoder slot 3 generates one down transition and one up transition;
- enabling vendor host-online mode exposed custom raw notices but
  suppressed the configured native controls during that test.

The host-online control plaintext is `01 01 10 00 <state>`, where state `03`
enables host processing and `00` disables it. The heartbeat plaintext is
`06 01 23 00 01`. Vendor code contains a 1000 ms path that resends online
state 3 plus the heartbeat. A host-online VibeKey Lite session was observed to
keep the AU05 lights awake past its saved five-minute standby delay; static
analysis alone cannot isolate which recurring report inhibits firmware idle.

VibeKey Lite therefore tracks AU05 input activity. When the saved standby
delay expires, it stops the heartbeat and sends online state 0 while keeping
both HID interfaces open. Power-on and active notices update displayed state
but deliberately do not resume host-online mode. The first native report is
allowed to return to neutral so its complete stored shortcut, including key-up,
finishes before host-online mode resumes. Subsequent inputs use host-side
single/double/hold gestures.
This handoff avoids modifying the saved standby and sleep timers. Normal stop
also sends state 0 synchronously before closing the HID interfaces.

While host-online mode is active, VibeKey Lite handles physical indices 0...5
and sends the configured actions through macOS. Encoder single press is delayed
by 280 ms to distinguish it from double press; a 650 ms hold is a separate
gesture. The device itself always stores a complete six-slot native profile,
including a real encoder single-press action instead of a reserved F18.

Automatic native recovery after heartbeat loss was observed once following an
abrupt host stop, which strongly suggests a firmware watchdog. Exact timeout,
reliability across crash/sleep/unplug, and byte-for-byte recovery of all six
slots remain controlled-test items. Normal quit and sleep do not depend on that
timeout because VibeKey Lite explicitly sends offline state 0.

Still unverified: hooks-mode persistence across reconnect and exact raw-notice
repeat behavior. Any future hooks test must first read and save the original
value, then restore that exact value.
